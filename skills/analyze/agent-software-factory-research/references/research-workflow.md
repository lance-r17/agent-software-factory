# 每日研究与交接工作流

## 1. 开工与唯一选题

1. 完整读取宿主 GitHub 流程，再按规定顺序执行站点检查、当日成功记录检查和安全同步。
2. 只有站点检查允许原地迭代时才继续。缺失项目按既有版本或快照恢复，不重建网站。
3. 同步后确认工作区干净、HEAD 与 `origin/main` 一致。main 领先、分叉或远端异常时停止。
4. 用 `scripts/select_candidate.py` 过滤 solutions 与 orphaned_entries 中已有 slug。不要仅凭候选的 pending 状态判断未收录。
5. 搜索同 slug 的打开和已关闭 Issue/PR；复用已有记录，核验范围后更新，不重复创建。

## 2. 选题 Issue 合同

Issue 至少写清：

- 官方仓库、候选版本或提交、核验日期。
- 研究范围、非目标、双语 Hash 路由和语言切换锚点保留。
- 官方资料与实际执行分离，禁止把 benchmark 官方成绩写成本站实测。
- 架构、工作流、组件、数据契约、部署、依赖、端口、密钥、模型、workspace、自动化、验收、故障、升级备份和安全边界。
- 中英文 SKILL.md、大纲、全文模态框、复制和下载。
- 生产构建、桌面与 375px 验收、网站版本、快照和方案 PR。
- PR 使用 `Closes #<issue>`，但只有用户人工 merge 后才允许关闭 Issue。

## 3. 证据层级

为每个关键事实标注来源和核验方式：

| 层级 | 含义 | 可写结论 |
| --- | --- | --- |
| 官方资料 | Release、源码、官方文档、论文、许可证 | “官方声明/官方提供……” |
| 本地实测 | 在隔离环境实际运行并保留命令和输出 | “本次实测通过/失败……” |
| 社区经验 | 可追溯到具体 Issue、讨论或文章 | “社区报告……”，不能替代官方或实测 |

核验等级：

- A：执行了目标端到端流程，并明确数据集、模型、环境和结果。
- B：只完成源码、安装、导入、CLI 或依赖兼容检查。
- C：只完成文档和源码整理。

不要为了提高等级执行未授权的高成本模型或基准任务。实测失败也是有效结果，应记录失败、根因和可复现修复，而不是删除证据。

## 4. 研究顺序

1. 固定官方 Release、tag/commit、许可证和核验日期。
2. 读官方 README、部署文档、源码入口和配置样例，梳理真实架构与数据流。
3. 检查依赖是否锁定、运行时版本、外部服务、密钥、端口、workspace 和输出目录。
4. 在 `/tmp` 或其他隔离目录验证源码包、依赖、导入和 CLI；不把模型 key 或 GitHub Token 放进容器。
5. 区分“命令来自官方”和“命令已执行”。故障速查应优先来自本次真实失败与修复。
6. 评估它在 Agent Software Factory 中的位置、缺失能力和不应拥有的权限。

## 5. GitHub 与状态交接

- 实现前从最新 main 创建 `solution/<slug>-<date>`；功能重构使用独立 feature 分支，不占每日方案份额。
- 网络失败按宿主手册最多重试一次。HTTPS 写操作使用 HTTP/1.1；需要 SSH 回退时严格执行指纹核验和临时部署密钥清理。
- 推送前检查工作区、变更清单、main 祖先关系和同名远端分支，禁止强推。
- 不提交 `dist/`、`node_modules/`、`.git/`、`state/`、`.github/workflows/` 或密钥。
- PR 写清版本、核验等级、实测范围、双语路由、来源、构建、交互验收、网站版本、快照、安全边界和 `Closes #<issue>`。
- 只创建或更新 PR，不自动 merge。使用宿主 `record_run.py` 记录结果；重新核验使用 `reverify.py`。
